Your tests start the VS Code that a variable such as `${VSCODE_EXECUTABLE}` names, and the libraries download nothing. Which builds the tests run against is your project's choice:

- A fixed version such as `1.141.0` gives reproducible runs.
- The newest Insiders build shows early when a new VS Code release breaks your tests.
- An installed VS Code, or a [fork](../forks/) such as VSCodium, tests what your users run.

## Getting the builds

[`@vscode/test-electron`](https://www.npmjs.com/package/@vscode/test-electron) downloads VS Code builds by version, `stable` or `insiders`, keeps them in its cache folder `.vscode-test` and returns the executable's path, as on [the getting-started page](../getting-started/#vs-code). An npm script per build in your extension's `package.json` downloads them before the tests; the example project has the first one:

```json
"scripts": {
    "download-vscode": "node -e \"require('@vscode/test-electron').downloadAndUnzipVSCode('1.141.0').then(console.log)\"",
    "download-vscode-insiders": "node -e \"require('@vscode/test-electron').downloadAndUnzipVSCode('insiders').then(console.log)\""
}
```

A second call takes a fixed version from the cache, while `insiders` looks for a newer build each time. The scripts print the executable's path, on Linux `.vscode-test/vscode-linux-x64-1.141.0/code` and `.vscode-test/vscode-linux-x64-insiders/code-insiders`.

## A profile per build

The workbench's DOM can differ between VS Code versions, so a locator that works with one version may fail with another. Because the [workbench keywords](../workbench-keywords/) take their locators from variables, a version with other locators needs no other keywords: a [RobotCode](https://robotcode.io) profile in `robot.toml` sets the variables for that version, together with its executable.

The example project's `robot.toml` sets `VSCODE_EXECUTABLE` to the VS Code that its npm script downloads, and has one profile for locators, `locator-override`, which replaces the command palette locator with an equivalent selector to show the mechanism:

<Code code={robotToml} lang="toml" title="robot.toml" />

A real project adds a profile for each VS Code build, or fork, and sets `VSCODE_EXECUTABLE` and the locators that differ in it:

```toml
[profiles.vscode-insiders]
description = "Run the tests against the newest VS Code Insiders"
extend-variables = { VSCODE_EXECUTABLE = ".vscode-test/vscode-linux-x64-insiders/code-insiders" }
```

Select a profile with `-p`:

```sh
robotcode -p vscode-insiders robot
```

Profile variables override the variables of `robot.toml` and the defaults in the resources, like variables given on the command line. To test several VS Code builds, for example on CI, run the tests once per profile.

Without RobotCode, pass the variables with `--variable` or collect them in a variable file per build and pass it with `--variablefile`.

## Personal settings

Settings that only apply to your machine, such as an installed VS Code or the paths of another platform, go into a `.robot.toml` next to `robot.toml`. RobotCode reads it after `robot.toml`, and it is not committed. Use `extend-variables` there: a `variables` table would replace all variables of `robot.toml`, not only the ones it names:

```toml
[extend-variables]
VSCODE_EXECUTABLE = "/usr/share/code/code"
```
